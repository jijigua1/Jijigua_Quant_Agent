# 数据版本、历史修订和可复现性

原始 daily_update PKL 每次可能重写完整历史，文件路径不是数据版本。发布批次必须锁定六文件 SHA-256、字节数、inode/mtime 采样、实际末交易日、5,427 代码轴、字段/单位、质量结论、生产者版本及发布日期。`capture_source()` 先后核对整个六文件组，混版或半写立即拒绝；新哈希不能自动提升认证等级。

本地原型的 `publish()` 采用**不可覆盖基线 + 日期增量**。第一个 Train/Validation 发布仅含各自日期范围的六个 `float64` `.npy`；新增日或改写日单独保存为 `parent_id` 指向前一版的小批次。每个文件、父 manifest 有 SHA-256；读者按链合成指定版本，旧目录不修改。合成测试证明 2020-01-03 修订后，v1 仍返回旧值，v2 返回新值。若修订既有日期，必须记录修订日期/单元计数及原因；大量回溯（例如 2026-08 的复权重建）进入隔离审核，不自动进研究资源。32 层增量后需审批新基线压实；不得删除旧基线和历史任务引用。

预算：发布原型单次上限 1GB 原始数值，研究读单次默认 200 万单元；六原始字段 2020–2025 基线大约 `1455×5427×6×8 ≈ 379 MB`（估算，不是已生成文件大小），单交易日六字段约 261KB。六个原始 PKL 哈希检查顺序读约 491MB，不复制；完整新版本差异分析仍需受限发布进程解码并比较重叠历史，**当前未在服务器运行**。若真实内存/磁盘超预算，则拒绝而非扩大进程权限。

研究实验应固定 `release_id + manifest_sha256 + source_sha256_by_field + data_end + code/params_sha256`。缓存键包含全部指纹；旧缓存不得伪装成今日数据。`/hy-tmp` 是可清理实例本地盘，批准发布前须约定持久目的地和备份频率；不能因文件在 `/hy-tmp` 存在就承诺长期可复现。原始文件、既有主 Agent 账本均不迁移。
